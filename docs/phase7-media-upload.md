# Seller media upload boundary

Buyer-facing images/videos remain publicly readable through Cloudinary. Writes now go through `/api/media/upload`; the old mobile media-config route returns 410. The browser and Flutter clients never receive an upload preset, Cloudinary API key or API secret. The route accepts a current seller session (cookie or mobile bearer), checks current user activity and store ownership/role, limits the multipart request to 51 MiB before parsing, validates file kind/MIME/extension/signature and image decoding, then chooses a random ID under `todijo/sellers/{storeId}/{kind}/`. No caller-supplied folder or public ID is accepted. Cloudinary upload uses server-side Basic authentication with `overwrite=false`; the returned URL, resource type and public ID are checked before returning them to the caller. Server-side CJ media copying uses the same private Cloudinary credentials and a separate supplier-products prefix.

Required deployment configuration: `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME`, server-only `CLOUDINARY_API_KEY` and `CLOUDINARY_API_SECRET`. Keep the API secret out of browser bundles, Flutter, logs and build arguments. Disable/delete the previously public unsigned Cloudinary upload preset at the provider before exposing the new runtime. This provider-console action cannot be verified from the repository. Do not keep it enabled as a fallback. Ensure Traefik request-body limits permit the chosen 51 MiB maximum only on this route, with appropriate request rate/abuse controls and storage quota monitoring.

The route never returns private media; products, variant images, logos, banners and videos continue to use Cloudinary public delivery URLs. CMS/news currently reference URLs rather than using a generic public signing/upload endpoint. Provider-side limits, moderation, retained old objects and old unsigned-preset revocation require operational verification. A production upload cannot be certified without the server-only Cloudinary credentials and provider access.

## Required Cloudinary console action before deployment

The legacy preset name is **not stored in this checkpoint**: it was supplied by the former `NEXT_PUBLIC_CLOUDINARY_UPLOAD_PRESET` deployment environment variable. An authorized operator must read that variable's **name/value mapping privately** in the currently deployed environment (do not paste the value into logs or a ticket), find the exact matching preset under Cloudinary upload settings for the configured cloud, confirm it is unsigned, and disable/delete that exact preset. Check whether any other website still depends on it before removal. Verify an unauthenticated request using that preset is rejected by Cloudinary, then verify a seller-owned upload through `/api/media/upload` succeeds with server-only credentials while anonymous and cross-store writes fail. Rotate credentials if the former preset or API keys were exposed. None of these provider-console checks was performed in Phase 8 because no Cloudinary account access or server-only credentials were available.
