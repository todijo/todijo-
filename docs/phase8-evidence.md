# Phase 8 infrastructure evidence and unresolved live gates

Date: 25 September 2026. All database measurements used a new PostgreSQL 17.10 cluster under a temporary directory, bound to `127.0.0.1:55432`; no production or existing local PostgreSQL service was modified.

## Executed locally

- `npx prisma migrate deploy` applied all 59 migrations to empty `todijo_e2e`. Full backend suite: 1,285 passed, zero failed or skipped with `DATABASE_URL` pointing only to that disposable database.
- A custom-format `pg_dump` of synthetic users/store and the complete schema was 324,280 bytes. The verified disposable database was dropped/recreated and `pg_restore --exit-on-error` succeeded in about 1.5 seconds. Checks found all 59 migration records, two users, one seller-owned store, the store FK, unique user-email index and global loyalty OFF. See `phase7-recovery-runbook.md` for exact commands and scope limits.
- A second disposable database received the 57 pre-loyalty migration SQL files and synthetic buyer, seller, store, product, order and order-item rows. Both pending loyalty SQL files applied in approximately 232 ms and 136 ms on this tiny dataset. Existing rows survived; the funding-source check and platform-funding unique index were present; global loyalty remained OFF. A local Next.js process using that database served `/api/health` with HTTP 200 and was stopped. These are not production-scale lock measurements.
- After validation, the dedicated PostgreSQL cluster was stopped. Its two temporary cluster directories and synthetic-only dump were deleted from Temp after checking their exact resolved paths. No existing local database service, valuable database or production data was removed.
- After the bounded buyer-history fix, a *new* disposable PostgreSQL 17.10 cluster was initialized at a unique Temp path, bound to `127.0.0.1:55432` only, and all 59 migrations were deployed again. The full backend suite passed **1,287/1,287 with zero skips**. It was stopped and its exact resolved Temp directory was verified and removed. Flutter analyze reported zero issues; all 137 Flutter tests passed; TypeScript, Prisma validate, web production build, Android debug and release builds with `TODIJO_API_ORIGIN=https://todijo.com`, `git diff --check`, and production `npm audit` passed (zero known vulnerabilities). No APK or local SDK/cache was added to Git.
- Synthetic 2,000-order buyer history before the fix: `listBuyerOrders` returned 2,000 fully related records in 423 ms and serialized to 3,900,680 bytes on this local machine. The underlying indexed/filtered order scan itself took about 1.3 ms after `ANALYZE`; relation fetching and serialization dominated. This confirmed an avoidable unbounded history response. The responsive buyer order page and authenticated mobile API now use a buyer-scoped, stable 20-order page with one-row overfetch for `hasMore`; Flutter loads additional pages on demand. Order detail remains individually buyer-scoped. The seller-dashboard history query for the same 2,000 orders took 173 ms and materialized 556,001 bytes server-side before aggregation; this remains a launch scaling watch item, not a production latency measurement. The buyer dashboard's aggregate statistics still read historical rows server-side and should be watched at larger volumes, but no longer represents the buyer history API response.

## Not verified, hence launch gates

- Recheck on 25 September still found no Docker CLI/Desktop, Podman or WSL2 runtime. An actual production image build, final-image inventory, non-root runtime check and container startup test remain unperformed. The Dockerfile copies `packages/contracts` before `npm ci`, and the runner declares `USER nextjs`; `.dockerignore` excludes `.env*` except the non-secret example, the entire Flutter `mobile/` tree, test output and Git metadata. These are static findings only. On a Docker-capable Linux CI host or Windows Docker Desktop/WSL2 machine, build from the reviewed commit with `docker build --no-cache -t todijo:phase8 .`, inspect the resulting image/layers and `docker image inspect` user, then start it only against isolated disposable configuration and smoke `/api/health`. Do not connect that test container to production DB.
- No Cloudinary production credentials or console access was available. The exact old unsigned preset name exists only in the deployed `NEXT_PUBLIC_CLOUDINARY_UPLOAD_PRESET` setting, not in this checkout. Provider-side disablement and live authorized upload must be verified by an operator.
- This repository contains no deployed Traefik/Coolify network configuration. The trusted-proxy header injection, ingress isolation and live spoofing checks remain unverified.
- No live Stripe account/dashboard access, CJ platform credentials, or production environment inventory was available. No financial/provider mutation was attempted. Live account, webhook, Connect, CJ catalog access, wallet status and runner schedules remain operational gates.
- No safe authenticated Buyer/Seller/Admin test accounts or iOS/macOS runtime were available for cross-platform end-to-end certification. Source tests and builds cannot substitute for those walkthroughs. Read-only public production browser inspection did load the French homepage with real catalog data and a product detail page with images, variants, price, stock, shipping estimate, and add-to-cart control. At a 390-pixel browser viewport, bottom navigation was visible and the page had no horizontal overflow. No purchase or account mutation was attempted; the observed browser session was not treated as a safe test account.
- This disposable backup drill did not validate production backup retention, production-sized restore duration, Cloudinary/R2 media recovery, Stripe webhook replay or a real deployment rollback.

Do not deploy solely on the basis of this document. Follow `production-operations-runbook.md`; keep global loyalty and CJ automatic fulfillment disabled until separately authorized.
