# Phase 7 financial and supplier code review

This is a source-level review, **not** live provider certification. No production Stripe/CJ mutation or migration was performed.

## Stripe

- Checkout creation uses `lib/payments.ts` and a buyer/request-scoped idempotency key; a mobile success/cancel deep link is navigation, not payment proof. Paid order state is finalized by the signature-checked Stripe webhook path (`lib/stripe-webhook-request.ts`, `lib/stripe.ts`, `app/api/stripe/webhook/route.ts`). The webhook persists event identity and handles duplicate/replayed events. Read the persisted order/payment state after return; never infer success from the URL.
- Connect account creation uses a user-scoped idempotency key; transfer submission in `lib/seller-transfers.ts` requires a verified shipment, account readiness and a durable claim. Ambiguous transfer attempts retain amount/key; definite failures rotate a retry generation. Refund and transfer reversal operations remain separate from return/dispute status decisions. Loyalty liabilities and seller/platform funding allocations are kept in the server-side ledger, not Flutter.
- Live readiness remains unverified: production Stripe mode/account, webhook signing secret and subscribed events, connected seller restrictions, payout settings, replay delivery, settlement balances, partial/zero-cash checkout and refund reconciliation must be checked in the Stripe dashboard and a controlled provider test. Do not perform real financial mutations merely to close this checklist.

## CJ exact behavior

- Successful payment creates/upserts supplier-fulfillment rows with deterministic external references. Platform-owned connected CJ rows can be `PENDING`; seller-owned CJ rows are `MANUAL_ACTION_REQUIRED` and require the existing explicit Admin submission path after current dropshipping permission, store, connection and order-item ownership checks (`lib/suppliers/supplier-fulfillment.ts`). A seller cannot directly submit another seller's order.
- **Automatic creation after payment is conditional:** only if `CJ_AUTOMATIC_FULFILLMENT_ENABLED=true` does the paid Stripe webhook invoke `processOrderSupplierFulfillments`. The default/required pre-launch setting remains false. With false, no CJ order is automatically created or paid merely because the buyer paid Todijo.
- The CJ `createOrderV2` call uses `payType: 2`, a CJ balance-payment request in the same provider operation (`lib/suppliers/cj-fulfillment-client.ts`). Thus, when the authorized submission actually runs and CJ accepts it, order creation and CJ wallet payment are requested together; there is no separate Flutter-controlled CJ payment. Shipment and tracking are **not** automatically fulfilled by Todijo: CJ status/logistics are read by the existing sync path and persisted by fulfillment ID/tracking number. Seller-owned submissions remain Admin-controlled even if the platform auto flag is true.
- Missing/disconnected platform CJ access or invalid mapping leaves the row blocked/manual; insufficient wallet funds and definite provider failures become persisted retry/manual states. Ambiguous responses are reconciled by external reference before any resubmission; never blindly place a second order. Provider outage or disabled credentials do not authorize a bypass. Operator review of balance, retries, ambiguous claims and tracking sync remains necessary.

## Pending loyalty migrations

`20260924120000_add_loyalty_ledger` adds default-off settings/eligibility flags, order/refund accounting columns, grants, reservations, ledger and constraints. `20260924190000_add_platform_funded_loyalty` adds explicit seller-reserve/platform funding attribution, platform funding/attestation tables and integrity checks. Neither migration drops existing tables or existing balance/order data. The second assumes the first has applied. Existing seller grants receive the `SELLER_RESERVE` default; platform grants require explicit attributed records.

These migrations still require a fresh backup, isolated restore rehearsal, pre-migration data/constraint checks, a controlled lock window, `npx prisma migrate deploy`, inspection of `_prisma_migrations` and read-only post-migration accounting checks. Table alteration/default/check/foreign-key/index creation can acquire locks and may fail on unexpected historical data; do not apply under uncontrolled production load. Applied migration files must not be edited. Use a reviewed forward fix or approved restore strategy rather than destructive rollback. Global loyalty stays OFF until separate financial/operational authorization.
